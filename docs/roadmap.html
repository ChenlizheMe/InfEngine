CURRENT CYCLE · 0.4.0 → 0.5.2 Roadmap

Infernux roadmap

From a working engine on Windows to cross-platform shipping, models running through the data plane, and agents that can build tools safely. No dates here, only what each step has to do before it counts as done.

Track issues Get started
0.4.0 · PLUGINS AND ASSETS
v0.4.0

Packaged assets and live plugin authoring

  • Repository packages use a package/ payload root and a standalone packer. Local authors work directly in their selected folder; scripts and assets under Packages refresh alongside project content.
  • Player content stays packed in Content.inxpkg. Authored asset paths resolve through cooked GUID identities, with real file access for payloads that require it.
0.4.0 · MULTIPLATFORM
v0.4.0

Four targets, one build workflow

  • 0.4.0 adds Windows and Linux Editors and Player exports for Windows, Linux, Android, and Web. The shared MultiPlatform040 project exercises gameplay, input, UI, and packaged asset reads.
  • Platform plugins carry their reusable build payloads. Hub manages Python and shared Android toolchains, while GUID-backed runtime content stays packed instead of exposing the project directory tree.
0.4.1–0.4.4 · PLUMBING
v0.4.1–0.4.4

Headless, semantics, replay, batch data

  • 0.4.1 brings Linux and windowless execution. 0.4.2 sets up the authoritative schemas. 0.4.3 does snapshot, delta and deterministic replay. 0.4.4 opens batch worlds and the tensor data plane.
  • Every one of these produces a versioned contract and acceptance evidence somebody else can measure. A private path that only survives inside a demo does not count.
0.5.0–0.5.2 · CONVERGENCE
v0.5.0–0.5.2

Tools an agent can build, on an engine that holds together

  • 0.5.0 formalises Engine Tools and draws a hard line between trusted and untrusted execution. 0.5.1 ships the distribution format for plugins and models, with their own tests run in a sandbox before anything lands in your project.
  • 0.5.2 has to string cross-platform Players, models, schemas, replay, batch worlds and tool governance into one path somebody can walk end to end, live.
Four tracks

Four tracks, and they all have to end up in one engine.

They share their plumbing. Platform contracts decide where a Player can run. Schemas decide who is allowed to change the world. Replay serves debugging and training equally well. Tool governance covers plugins and agents with the same machinery.

Shipping

  • One project exporting an Android APK/AAB and a Web package you can deploy as it is.
  • A Linux Player, plus windowless and offscreen runs for CI, servers and large-scale simulation.
  • Platform capabilities declared up front, and missing ones failing loudly. No silent downgrades; quiet fallback is a debugging nightmare.

Model data

  • Standard PyTorch right in the editor: develop, train, evaluate and export without switching environments.
  • A Player that carries only the inference runtime its platform needs. No CUDA Toolkit, no entire training stack riding along.
  • Every hop between Torch, DLPack and GPU buffers measured, and every copy written down in the docs.

Semantic world

  • Versioned reflection plus Command/Query schemas, so UI, Python and MCP read one definition instead of each reimplementing it.
  • World snapshot and delta, deterministic replay contracts, and batched create, step and reset.

Tools and ecosystem

  • An Engine Tool ships with its schema, permissions, tests, provenance, resource limits and lifecycle attached.
  • Plugins and models get a real distribution format, and their own tests run in a sandbox before anything enters your project.
  • Anything an agent builds clears the same bar as human-written code before it goes near someone else's project.
On the bench right now

The next three.

These have to close real shipping loops. Writing the architecture document does not count, and neither does getting one isolated demo to run.

Android Player vertical slice

Get a first APK onto real hardware with lifecycle, input, assets, audio, rendering, logs and a minimal portable scripting subset all working in one pass.

Web portability gate

Map out the native module, Python, rendering, storage and packaging boundaries in the browser first, then talk about compatibility and performance. This step will probably kill a few assumptions.

Torch entry and the inference backend

Native PyTorch stays in the editor. Which inference backend goes on Android and Web gets decided by measuring model coverage, latency, memory, package size and fallback behaviour, not by picking a favourite.
