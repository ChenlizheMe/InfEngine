The Doom generation of engines finished its job a long time ago. Unity and Unreal got the tools into everyone's hands, and now they are fumbling at what this era actually asks for, because whether a model or an agent can really use an engine comes down to its lowest-level data layout, threading model and tool boundaries. class Spin(InxComponent):
    speed: float = serialized_field(default=90.0, range=(0.0, 360.0))

MANIFESTO

AI-native is not a chat panel. It means world state you can pull out as a tensor in one call, training that runs inside the editor, and agent-built tools that carry a schema, permissions and tests. None of that can be retrofitted. It has to grow up from the core.

What we are betting on

Agents and the engine, wired together at the bottom.

You do not get there by hanging a plugin off a mature engine. How the data is laid out, who is allowed to release the GIL, where the tool boundary sits: all of it has to be decided again, from the core outward.

MISSION COMPLETE

The Doom generation already handed in its work

Pulling rendering, assets and gameplay out of one game and turning them into something you could reuse and license: id Tech settled that in 1993. It was the right problem then. Nobody needs to prove it again.

FUMBLING · RIGHT NOW

Unity and Unreal are patching AI on from outside

They did the universal-tooling part well. But Python stays a second-class citizen over there, world state comes out one getattr at a time, and whatever an agent is allowed to touch rests on a script behaving itself. A plugin cannot fix any of that.

WHAT WE ARE BUILDING

Start at the data plane and cut the path through

State sits in C++ as structs of arrays, and one call hands it to Python as a numpy array with the GIL released. An agent drives the same command system you do, and every capability it holds can be audited and taken back. This is the code we write every day.

House rules

Three rules we do not break.

These three regularly make us turn down things that look cool. They are written here so you can hold us to them.

1 · It has to be an engine you can ship a game with

Scenes, assets, rendering, physics, UI, animation and packaging stay working. If an AI feature does not make shipping a game better, it does not get merged, however good the demo looks.

2 · Python is not the scripting layer

Gameplay, editor extensions, render pipelines, asset workflows, training scripts: all Python. C++ and the GPU only own performance and deployment. The language you drive the engine with is the language you drive the model with.

3 · AI comes in the front door

UI, Python, MCP and agents all read the same schema and the same permission set. What a model can call is declared up front, so when it goes wrong you can trace it, undo it, and take the capability back. Without that, do not hand it an engine.

What is in 0.3.6

The parts you can already work with.

0.3.6 merged scene and UI authoring into one Hierarchy and fixed automatic updates in packaged Hub builds. The engine still moves fast, and we still change an interface when it turns out to be wrong.

SUBSYSTEM · RENDER

Vulkan render core

Forward, Forward+ and Deferred paths, PBR, per-camera shadows, MSAA. You describe the pipeline in Python and C++ compiles it into a RenderGraph and schedules it. Effects are reusable assets, and the GLSL is structured rather than one long string.

SUBSYSTEM · GPU VFX

Particle Graph on the GPU

GPU Particle Graph: an emitter plus Init, Update and Rendering stages. The typed graph compiles to runtime IR ahead of time, outputs sprites or meshes, and previews in the editor with parameters you can drag while it runs.

SUBSYSTEM · PHYSICS

Jolt physics

Jolt. Rigid bodies, colliders, scene queries, collision callbacks, layer filtering, transforms kept in sync with the scene. Its job system runs on the engine's own thread pool rather than spawning threads of its own.

PREVIEW · ANIMATION

2D and 3D animation

2D clips and sprite playback, embedded FBX takes, skeletal animation, skinned meshes, state-machine graphs, Timeline. All of it hangs off the same document and undo services, so the pieces do not fight each other.

SUBSYSTEM · EDITOR

12 panels, one command system

Hierarchy, Inspector, Scene/Game, Project, Console, UI, animation, Timeline and the graph editors all share one selection, command, shortcut, document, save and undo stack. Useful side effect: an agent drives the editor down exactly the path you do.

SUBSYSTEM · SCRIPT

Python gameplay layer

Component lifecycle, serialized inspector fields, coroutines, prefabs, hot reload. Close enough to Unity that you will not have to relearn much. Put @njit on a hot function and Numba takes it; where Numba is unavailable it falls back to pure Python instead of blowing up.

SUBSYSTEM · ASSETS

Assets and project pipeline

GUID identity, dependency indexing, imported Library artifacts, live previews, transactional documents. When you export a Player, authoring data and runtime content are two separate things.

SUBSYSTEM · DATA PLANE

Batch data bridge

batch_read(cubes, "position") hands you an (N, 3) numpy array in one call. The C++ side keeps that data as a struct of arrays and the GIL stays released for the trip. Writing back works the same way. This is what makes world state visible to a model at all.

EXTENSION · MCP · AGENTS

MCP Harness

An agent opens a real project window and drives it through the public workflows: frame-bounded input, semantic state reads, and a straight answer about where it got stuck. Development-time tool. It never ships inside your game.
